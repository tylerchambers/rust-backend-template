## Mission
Build a production-grade Rust multi-tenant SaaS backend template with a modular monolith, pragmatic hexagonal architecture, explicit composition root, PostgreSQL RLS, email magic-link authentication, server-side sessions, River jobs, optional Redis, and OpenAPI-generated clients.
## Non-negotiable decisions
- Current stable Rust pinned at initialization; current compatible dependencies, with no backward MSRV goal; Axum/Tower/Tokio; SQLx and PostgreSQL; SQL migrations.
- Domain has no HTTP, SQLx, Redis, or River dependencies. Application orchestrates use cases and narrow ports; adapters implement infrastructure; constructors wire dependencies.
- Global users, organizations and memberships. Shared-schema tenant tables protected by PostgreSQL RLS and app-layer policies.
- Email magic-link login and fresh email reauthentication for sensitive operations. Account access rests on mailbox control; no passkeys, credential enrollment/removal or separate recovery flow. Server-side hashed opaque secure cookie sessions retain revocation and CSRF protection.
- River owns durable jobs, retries, leases, schedules and worker execution. No homegrown task runner. Redis is optional for caching and distributed rate limits; PostgreSQL remains authoritative.
- OpenAPI contract and generated TypeScript client. Test against real PostgreSQL, including RLS and migrations.
- No speculative microservices, Kafka, generic DI container, or mandatory Redis.
## Delivery protocol for implementation agents
1. Read this page and all architecture subpages before implementation.
2. Claim one ticket; respect dependencies and avoid simultaneous edits to the same files or migrations.
3. For each ticket: write tests, implement, run checks, document evidence and commit/PR references. Do not mark complete merely because code exists.
4. Architectural changes require an ADR. Security decisions require adversarial tests.
5. Each ticket is independently verifiable. Status begins Not Started; no assignees or dates are implied.
## Workstreams
Foundation → persistence/tenancy → identity/auth → authorization → River/jobs and Redis → API/OpenAPI → integration and hardening.
## Definition of done
Fresh checkout can boot API and worker, migrate PostgreSQL, seed organizations, authenticate with email magic links and confirm fresh email reauthentication for sensitive operations, manage memberships, enforce RLS, run River jobs, expose OpenAPI and pass unit/integration/security/architecture CI. No tenant data leakage under adversarial tests.
## Open decisions / spikes
Validate current crate compatibility on the current stable Rust toolchain pinned at initialization; SQLx transaction/UoW ergonomics; River transaction integration and migration ownership; scanner-safe magic-link confirmation and email delivery; rate-limit failure mode; RLS administrative paths. No backward MSRV goal; select current compatible dependencies and do not assert an exact SQLx or other dependency version before compatibility validation. Approved scope change: email magic links replace passkeys and fresh email reauthentication replaces WebAuthn step-up; no credential management or separate recovery. Workstreams, ticket dependencies and unrelated architecture remain unchanged; implementation completion still requires evidence.
