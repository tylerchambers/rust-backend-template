## Authentication
Email magic-link authentication; mailbox control is the account-access trust anchor. Generate \>=256-bit CSPRNG tokens, persist only their hash/HMAC, use a short bounded TTL, and consume atomically exactly once with the successful authentication transaction. Bind tokens to the normalized email and purpose. Return the same initiation response for known and unknown addresses; rate-limit initiation and confirmation by IP and normalized email without disclosing account existence. Only create/resolve and verify an active identity after valid confirmation. GET renders an inert confirmation page and never consumes a token, creates a session or executes a sensitive operation; require explicit user confirmation via CSRF-protected POST, with browser/Origin checks to prevent login CSRF. Allow only validated local redirect targets; use trusted configured public URLs. Redact tokens and full magic-link URLs from logs/traces/errors; prevent leakage through referrers, third-party content and caching. Development uses an external email capture service; production uses an SMTP adapter with required transport security and secret configuration. Test SMTP delivery without using real personal mailboxes.
## Server sessions
Issue \>=256-bit CSPRNG opaque session token in __Host- prefixed Secure HttpOnly Path=/ cookie with deliberate SameSite policy. Persist hash/HMAC of token in PostgreSQL, never plaintext. Idle and absolute expiry; rotation on login/privilege change; revoke one/all sessions; audit session lifecycle. CSRF protection for state-changing cookie-authenticated requests; validate Origin/Referer as appropriate. Session identity and tenant authorization are resolved server-side.
## Fresh email reauthentication
Sensitive operations require a newly issued email link to the current verified mailbox, bound to user, current session, requested action and target. Apply the login token safeguards, short TTL and atomic one-time confirmation; GET must not authorize or execute the operation. Atomically consume the action-bound proof with authorization of that operation; require a new proof for another operation or after expiry. Record auth_time for auditing, but a recent login alone is not action-bound proof. This is mailbox reauthentication, not independent MFA or hardware binding; mailbox compromise enables account access, and stolen-cookie risk remains for ordinary operations until revocation or expiry.
## Authorization
Global users join organizations via memberships. Roles: owner/admin/member/viewer; typed permissions for organization, membership, project and billing capabilities. Use policy functions inside application use cases. Verify current membership, tenant, role and resource conditions; never trust JWT-style embedded permissions or stale cached grants. Last-owner invariants enforced transactionally.
## Email identity lifecycle and revocation
One verified primary login email per user, with normalized uniqueness and account-status enforcement. No passkeys, credential enrollment/removal, multiple login addresses, email-change workflow or separate recovery flow in this scope. Repeat access uses a new magic link to the same mailbox; loss of mailbox access has no separate application recovery path. Audit identity and session lifecycle without secrets. Disabled users cannot log in or use existing sessions. Membership removal revokes access immediately; session revocation cannot be masked by Redis staleness.
## Negative tests
Expired/invalid magic links; sequential and concurrent replay; wrong purpose/email binding; scanner GET or prefetch consuming authentication; login and action CSRF; account enumeration; initiation/confirmation rate-limit bypass; unsafe redirects; token leakage in logs/referrers; duplicate identity creation; disabled-account access; session fixation; expired/revoked cookie; privilege escalation; stale membership; cross-tenant access; wrong-user/session/action/target or expired/replayed reauthentication proof; stolen cookie without fresh email proof.
