# Architecture: capabilities inside hexagonal boundaries

## Model

```text
User --has Membership(is_admin) in--> Organization --contains--> Project
Organization --offers Invitation(email, is_admin) for--> joining User
Mailbox login --creates--> Session --identifies--> User
Session + current Membership --authorize--> tenant operations
Mutation --atomically publishes--> audit and applicable durable job
```

Admin access belongs to the membership, not the user. All members can work on
projects. Admins also manage invitations and membership and read the audit feed.
Invitation acceptance preserves an existing membership's admin flag. Project is
a behavior-bearing entity; query summaries, credentials, actors and job payloads do
not each need a business aggregate.

## Boundaries and navigation

```text
apps/server, apps/worker, apps/cli
                 |
             bootstrap
             /       \
           api    infrastructure
             \       /
             application
                  |
                domain
```

- Domain owns pure project mutations and shared value/permission rules.
- Application owns workflows, consumed ports and required consistency boundaries.
- API binds HTTP input/caller context, calls workflows and translates responses.
- Infrastructure owns PostgreSQL, SMTP, Redis, River and system implementations.
- Bootstrap constructs dependencies and owns process lifetimes; it is not a
  service locator queried by application code. App entrypoints stay thin.

Crate roots are module indexes with deliberate public exports. Organize by
capability inside each boundary, not a compulsory models/services/ports tree.
A cohesive application file may contain service, ports and query projections.
Create a directory only when a second responsibility justifies it.

Authentication owns login and session workflows.
Organizations owns creation/discovery, memberships owns member administration,
invitations owns join grants/delivery, and projects owns project reads and writes.
Administration owns the three privileged tenant reads: invitation history, audit
events and the member directory.
Shared actor, authority and commit/audit contracts do not belong to projects.
Ports live beside consumers: cache in projects, supplemental limiter in
authentication, mail contracts beside their sending workflows.

API resource modules own DTOs/handlers and embedded HTML pages. Router, state,
errors, contract, pagination, cookies, middleware and HTTP metrics are shared
adapter concerns. PostgreSQL modules own capability SQL/row mapping; a neutral
transaction owns tenant context, audit and commit. River handlers bind typed
arguments/tracing/outcomes and delegate named operations rather than hiding SQL
and delivery inside registration closures. Bootstrap separates configuration,
construction, process entrypoints and telemetry.

One concrete PostgreSQL transaction implements several narrow interfaces.
Do not grant project consumers membership mutation or split a workflow into
independently committing repositories for the sake of file symmetry.

`just check` enforces the workspace crate dependency boundaries.

## React workspace

In `apps/frontend/src`, the UI uses `isAdmin` to offer administrative actions.
It cannot assume another admin exists on an unloaded roster page. The server
checks current membership and the last-admin constraint on every relevant write.

`infrastructure` owns SDK requests, response validation and query options per
resource. Workspace lists use a full page's final ID as their next cursor;
session enumeration uses its own endpoint's continuation rule. `presentation`
owns forms, selections and rendering. `application` owns React synchronization
and access to the dependencies supplied at startup.

Two boundaries matter when changing these flows:

- The identity query lives outside the account's query client. Switching accounts
  must discard the old workspace, even when an old request finishes late.
- A project rename submits the version the editor reviewed. Refreshing the list
  must not silently rebase an open draft or overwrite its proposed name.

## Consistency contracts

**Create organization:** validate name/generate ID; begin scoped transaction;
lock and validate live caller; insert organization and its first admin; audit; commit.

**Project change:** validate current authority; apply domain name/version rules;
persist with SQL expected-version protection; enqueue change and audit; commit.
Both domain and SQL concurrency checks matter. Cache invalidation follows commit.

**Membership change:** serialize organization writers; lock all actor/target
identities in deterministic order before authority reads; revalidate current
session and admin authority; prevent removal or demotion of the last admin;
mutate, audit and commit. Changing admin access retires the target's existing
sessions in the same transaction. Removal and a no-op change do not globally
retire sessions. The confirmation dialog prevents accidental submissions; it
is not a credential or a server authorization check.

## Authority and security

PostgreSQL is identity/session/membership authority. Tenant context is
transaction-local; tenant tables use FORCE RLS. Runtime cannot be table owner,
superuser or BYPASSRLS. Account discovery has SELECT-only self-membership
visibility, not mutable active-tenant state. `/v1/me` returns only the caller's
ID and verified email, even without a membership. Any tenant member can read
IDs and admin flags on `/members`; only admins can read tenant member
emails on `/member-directory`. The latter includes disabled accounts that
still hold a membership.

Invitation history shows each invitation's current state, not a delivery or
transition log. The audit feed exposes only already-recorded organization
events, never identity audit records. These two reads and the directory check
current admin authority in the same transaction as the query. Each page
returns up to 50 rows. Invitation history and directory entries use ascending
UUID order. Audit events use descending `(occurred_at, id)` order; the last
event ID anchors the next page within the same organization.

HTTP authentication does not replace transaction-time authority. Lock waits are
followed by fresh database-time validity checks. Preserve organization, identity,
session and membership locking order, including upfront target identity locks.

256-bit bearer secrets are SHA-256 hashed, never persisted raw in tables/jobs.
Sessions have database-authoritative absolute/idle expiry. Rotation preserves
stable session identity and revocation-only old-token handles. Old tokens cannot
authenticate but can revoke a delayed replacement credential.

GET confirmation pages are inert; explicit POST requires exact Origin and
unambiguous CSRF header/cookie. Fragments are cleared from browser history;
page submission reads the current CSRF cookie. Correlation IDs are generated by
the server. Mandatory socket-IP admission ignores forwarded headers. A proxy
shares that source bucket. Client/log errors exclude credentials, DSNs,
mailboxes, bodies and raw dependency causes.

## Effects, libraries and operations

SQLx owns application migrations; River owns its independent schema, retry,
rescue, scheduling and leases. Durable enqueue shares business commit. Project
indexing is an idempotent latest-state projection, not an event store.

Invitation jobs carry IDs, not secrets. Delivery prepares a fresh hash for a
still-live invitation, commits, then sends SMTP. Ambiguous SMTP acceptance may
duplicate mail; retry invalidates the earlier link. Login mail is sent
directly after issue commit and has no durable retry. No exactly-once claim.

Optional Redis is nonauthoritative. Cache failure falls back to PostgreSQL;
population/invalidation is best effort and eventually consistent. Configured
supplemental security limiting fails closed. Required budgets stay in PostgreSQL.

Maintain library ownership of parsing, transport and instrumentation; see
[ADR 002](adr-002-library-reuse.md) for session/CSRF integration rationale.
No generic repository framework, event bus, DI container or custom queue engine.
Operational readiness/combined metrics are bootstrap-owned routes outside API
security/trace layers; HTTP-only metrics remains API-owned.

## Contracts, tests and scope

Rust/Utoipa defines the API. `just openapi` writes the checked-in OpenAPI
document and generates the SDK types with openapi-typescript. Change the Rust
definitions, not the generated files.

Policy and adapter tests live in their crates; client tests live in the SDK.
Use real PostgreSQL to exercise transactions, RLS and races. See
[Contributing](../CONTRIBUTING.md) for the test recipes.

Migrations assume a dedicated cluster and create the runtime role. Do not
rewrite applied migrations. Before deploying an upgrade, test compatibility
against the revisions and data you actually run.

The [specification index](spec/README.md) records the provenance of the
historical snapshots.
